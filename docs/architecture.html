Architecture

How the parts fit together, and where the query library lives in each of the two databases.

The repository is one pipeline with two front doors. A single query engine answers ArcGIS REST requests; everything else is either a producer of its data, a renderer of its answers, or a generator kept in step with it. The library of 31 analytical questions is not a module the UI imports — it is a table of the service, discovered over REST like any other table.

1. The whole picture

Three bands. Top: one source file, three derivations — none of them a second copy to maintain. Middle: the engine, with a runtime injected underneath it so the same code runs on Node and in the browser. Bottom: the consumers, all of them speaking REST.

The service publishes two layers over one REST surface:

RestParams holds where / groupByFieldsForStatistics / outStatistics / having / orderByFields, never a SELECT — see the query catalog for why that distinction is the whole point of the pattern.

The Chart* columns are the presentation contract. No response type is declared for any question anywhere in this pipeline, so these columns are the only place the shape of an answer is written down: which column is the category axis, which are the measures, what splits into series. viewer/js/result-chart.js obeys them and falls back to inferring from the shape of the rows only for results that have no contract, such as anything run from the SQL console. HasChart = 0 is a statement in its own right — a single figure or a list of features is not a chart — and the catalog pattern explains why a declared contract and an inferred one are not the same kind of thing.

ParamSpec is the extension contract: the parameters a question may be varied by, each with the type, the range its author ratified, and where the value lands in the definition. Six questions declare one — "top 5 categories" is the obvious case, and Q27's "stuck for more than 30 days" is the interesting one, because 30 is a policy, not a fact:

[{ "name": "days", "label": "Open longer than (days)", "type": "int",
   "min": 1, "max": 365, "default": 30,
   "binds": [{ "in": "rest", "key": "where", "template": "Status <> 'Closed' AND … > {v}" },
             { "in": "tsql", "find": "… GETDATE()) > 30", "template": "… GETDATE()) > {v}" }] }]

The binding is data, and it never hands the client a fragment of query text to compose. The entry stores the default rendering — resultRecordCount: 5 and TOP 5 stay literal — so a client that ignores ParamSpec still replays the question exactly as ratified, and binding the declared default has to reproduce the published definition byte for byte. test/params.test.js asserts that for every parameter, which is what makes a default the ratified question rather than merely a sensible number.

How it is set up in the mock database

There is no DDL file for layer 1, because the table is built from the field list at start-up. featureService.load() creates both layers the same way, in the same in-memory SQLite database:

db.exec(`CREATE TABLE _QueryLibrary (${CATALOG_FIELDS.map((f) => `"${f.name}" ${sqlTypeOf(f)}`).join(', ')})`);

It then inserts catalogRows() and registers a layer descriptor — { id: 1, name: 'QueryLibrary', table: '_QueryLibrary', fields: CATALOG_FIELDS, oid: 'ObjectID', displayField: 'Question', timeField: null, geometry: false } — alongside layer 0's. From that point the query methods are layer-agnostic: svc.query(params, 1) takes the same where, outFields, outStatistics and orderByFields path as a query against the points, which is why the catalog can report on itself (…/1/query?groupByFieldsForStatistics=Portability). The database is read-only (PRAGMA query_only plus a statement filter), both layers alike.

So adding a question changes one array. The table's rows, the .http file and the T-SQL catalogue all follow from npm run build, and nothing in the viewer changes at all.

How it is set up in SQL Server

The SQL Server side exists for comparison — proving the T-SQL and the REST request give the same answer on identical data — so it carries the library in the simplest form that supports that:

ScriptObjectForm
sql/01_ServiceRequest_table.sqldbo.ServiceRequest, dbo.GeoJsonDocumenttables plus three indexes; Shape is a computed GEOGRAPHY::Point
sql/02_import_geojson.sqldbo.vw_ServiceRequest_GeoJson, dbo.usp_ImportServiceRequestGeoJsonview and stored proc over OPENJSON, epoch ms to SAST

An entry is executed by number, through the proc form in the same script — the T-SQL counterpart of replaying a row's RestParams against layer 0:

EXEC dbo.usp_RunLibraryQuery @QueryNumber = 14;                 -- run it
EXEC dbo.usp_RunLibraryQuery @QueryNumber = 14, @Execute = 0;    -- return the statement only

It resolves SQLText from the view and hands it to sys.sp_executesql, throwing 50010 for a number that is not in the catalogue. The underlying two lines work as well, if a caller would rather hold the statement itself:

DECLARE @sql NVARCHAR(MAX) = (SELECT SQLText FROM dbo.vw_QueryLibrary WHERE QueryNumber = 14);
EXEC sp_executesql @sql;

Note what this deliberately is not. It is not a physical table, so there is no load step and no stored row that can drift from the library — regenerate the file, re-run it, and the view is current. And it is not the same schema as layer 1: it has no Portability, RequestCount, Transforms, RestParams or TransformSpec, because those describe the REST half of an entry and mean nothing to a client that already holds a T-SQL statement. The two catalogues are two projections of one source, each carrying the columns its own execution path can act on.

The Chart* columns and ParamSpec are the exceptions that show the rule: they appear in both, because they describe the question and its answer rather than the route taken to it. Whichever way a client resolves query 14 — replaying RestParams against layer 0, or EXEC dbo.usp_RunLibraryQuery @QueryNumber = 14 — it gets the same rows, the same instruction for drawing them, and the same statement of what a user is allowed to change. The proc runs SQLText as published; binding a parameter means rendering the declared template over the declared text, which the REST side does on the trusted side at /FeatureServer/1/execute.

4. The two REST hops, end to end

sequenceDiagram autonumber participant V as viewer participant R as restRouter.js participant E as featureService.js V->>R: GET /FeatureServer/1/query (where=1=1, outFields=*) R->>E: svc.query(params, 1) E-->>V: 31 catalog rows Note over V: the run panels list them, grouped by Category V->>R: POST /FeatureServer/0/query, the RestParams of that row R->>E: svc.query(params, 0) E-->>V: rows Note over V: runner.js applies the TransformSpec,<br/>result-chart.js draws it per the Chart* columns

Both hops are the standard ArcGIS query operation, and nothing about Q14 exists in the client.

And one hop that is deliberately not generic

sequenceDiagram autonumber participant C as client participant X as /1/execute participant E as featureService.js C->>X: GET ?q=27&top=3&days=90 X->>E: svc.query(where QueryNumber = 27, layer 1) E-->>X: the catalog row Note over X: bindEntry validates 3 and 90<br/>against the row's ParamSpec X->>E: svc.query(the bound RestParams, layer 0) E-->>X: rows Note over X: runner.js applies the TransformSpec here,<br/>not in the client X-->>C: question, parameters, rows, chart contract

/FeatureServer/1/execute is a mock extension, like /0/sql, and it exists to make a point the two generic hops cannot. Its input type is a question number plus the parameters that question declares — a where or an outStatistics sent to it is refused, not ignored. It resolves the row through its own layer 1, binds on the trusted side, executes, and applies the client-side transform before answering. That is the forwarding tier of the catalog pattern: it restores the narrow input type the pattern rests on, and it knows nothing about any individual question. The viewer still replays rows against layer 0, because that is the honest demonstration of what a FeatureServer alone can do; the tier is what you add when the bounds have to be enforced rather than published.
