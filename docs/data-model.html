Data model: generic public service request

The layer is a generic council "report a problem" record. It holds only what a member of the public submits plus the council's lifecycle dates. It contains no internal system names, staff or contractor details, or complainant contact data. Coordinates are synthetic points in and around Cape Town.

How the data behaves

Everything is synthetic and generated from a seed, so a given seed always produces the same file. The generator shapes it so the query library has something real to find:

  • Seasonality follows the southern hemisphere: winter peaks for drains, flooding, roads, trees and streetlights; summer peaks for water, parks and noise.
  • Channel correlates with urgency. Hazards, noise and major leaks arrive by Phone more often than routine requests, which skew towards App and Online form.
  • Resolution time varies by sub-category: each one has a median, scattered log-normally, and requests whose description reads as urgent close faster. Anything that would still be open at the snapshot time stays Open or In Progress, which is what gives the backlog and ageing queries a realistic spread.
  • Suburb is sometimes NULL, standing in for a report that gave only a map pin — more often on App reports (8%) than on other channels (3%).

Deliberate data defects (exercised by queries 57–60)

  • Closed with no DtCompleted
  • DtCompleted earlier than DtLogged
  • DtCompleted set while Status is not Closed
  • Suburb NULL (pin-only app reports), and empty or NULL Description
